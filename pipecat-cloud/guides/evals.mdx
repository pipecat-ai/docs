---
title: "Evals"
description: "Run Pipecat scenario evals against a deployed Pipecat Cloud agent, or judge a finished session, with the CLI or the REST API."
---

An eval run checks a deployed agent against a [Pipecat eval scenario](/pipecat/evals/overview) without you hosting the harness. You send a scenario, Pipecat Cloud runs it, and you read back a verdict, the reasons for it, the metrics, and the conversation.

<Warning>
  A synthetic eval run starts real sessions of your deployed agent, and the
  agent calls its real tools: bookings, emails, payments, database writes. Run
  evals against an agent that uses test credentials or against a staging
  deployment, never against an agent wired to production systems. A session run
  starts no session and calls no tools.
</Warning>

## Run kinds

| Kind        | What it does                                                                                                                                                                                       |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `synthetic` | A simulated caller, or the scripted turns of the scenario, holds a conversation with a new session of your deployed agent. The default.                                                            |
| `session`   | Judges a session of the agent that has already ended, by the scenario's `success:` and `metrics:`. It starts no session. Needs [conversation publishing](#publish-conversations-for-session-runs). |

Both kinds take the same scenario files you use with [`pipecat eval`](/api-reference/cli/eval), and both end with a verdict of `passed` or `failed` when they can reach one.

## Write a scenario

A scenario file is a YAML file in the [format described in the Pipecat evals docs](/pipecat/evals/scenario-configuration). A run sends the scenario file and the files it includes with `!include`, and nothing else.

### A synthetic scenario

`scenarios/greeting.yaml` is a [scripted scenario](/pipecat/evals/scripted-scenarios) that checks the agent's reply to one question:

```yaml scenarios/greeting.yaml
name: greeting

scenarios:
  - name: capital_question
    turns:
      - user: "What is the capital of France?"
        expect:
          - event: response
            eval: "the response says the capital of France is Paris"
```

A [simulated scenario](/pipecat/evals/simulated-scenarios) works the same way. An LLM plays the caller, and the judge decides `success:` once the call is over.

### A session scenario

A session run judges a conversation that already happened, so it has no caller to play. It uses the scenario's `success:` and `metrics:`. The scenario file still needs the `persona:` and `goal:` that the simulated format requires.

```yaml scenarios/book_table.yaml
name: book_table

scenarios:
  - name: judged
    persona: "Jamie, booking dinner for two tonight at 6 PM."
    goal: "Book a table for two at 6 PM, then end the call."

    success: "the bot confirmed a reservation for two at 6 PM (a booking tool was called)"

    metrics:
      - name: politeness
        criterion: "the reply is courteous, never curt or dismissive"
        min_score: 1
      - measure: function_calls
        calls:
          - name: book_table
            args: { party_size: 2 }
```

Measured metrics that need a live run, such as `latency`, are not scored on a session run. See [Metrics](/pipecat/evals/simulated-scenarios#metrics) for the judged and measured kinds.

The `result.ignored` field of a finished run lists the scenario's keys that had no effect, the first 20 of them. `result.ignoredTotal` counts them all.

## Publish conversations for session runs

A session run needs the session's conversation, and an agent doesn't publish it by default. To publish it, set `PCC_EVAL_CONVERSATIONS=true` in the agent's environment, for example in its [secret set](/pipecat-cloud/fundamentals/secrets):

```shell
pipecat cloud secrets set my-secrets PCC_EVAL_CONVERSATIONS=true
```

Publishing needs:

- The Pipecat Cloud base image `0.2.12` or later.
- `pipecat-ai` 1.13 or later in the agent.

Then deploy or restart the agent. Only sessions that start afterwards publish a conversation. The published conversation includes what the caller and the agent said and the agent's tool calls with their arguments.

- A session whose process is killed, by a crash or a forced stop, publishes nothing.
- Setting `PCC_EXCLUDE_CONTENT=true` or `PCC_WITHHOLD_CONTENT=true` keeps the content out of the conversation, so a session run on that agent ends as `not_started`.
- A session run on a session that hasn't ended is refused with `409`.

Synthetic runs don't need this setting.

## What is sent to OpenAI

Eval runs use OpenAI models, on Daily's OpenAI account with zero data retention:

- **A synthetic run** sends the scenario and the whole conversation with your agent. The simulated caller (the persona) and the judge are both OpenAI models.
- **A session run** sends the conversation your agent published and the scenario's criteria to the judge.

The conversation includes the tool calls the agent made and their arguments.

For a session run, enable [conversation publishing](#publish-conversations-for-session-runs) only for agents whose conversations you're willing to send.

## Run an eval with the CLI

The commands live under `pipecat cloud eval`. They need an authenticated CLI ([`pipecat cloud auth login`](/api-reference/cli/cloud/auth), or a [personal access token](/pipecat-cloud/guides/personal-access-tokens)). See the [command reference](/api-reference/cli/cloud/eval) for every option.

Run a synthetic scenario and wait for the verdict:

```shell
pipecat cloud eval run my-agent scenarios/greeting.yaml --scenario capital_question --wait
```

Judge a session that has ended:

```shell
pipecat cloud eval run my-agent scenarios/book_table.yaml --scenario judged --session 3b1f0f6e-7c1a-4e0e-9d47-0f4a5f0a9a11 --wait
```

Without `--wait`, the command prints the run's ID and status and returns. Check on it, list recent runs, or cancel it:

```shell
pipecat cloud eval status RUN_ID --agent my-agent --wait
pipecat cloud eval list my-agent
pipecat cloud eval cancel RUN_ID --agent my-agent
```

With `--wait`, the exit code is the verdict, so a script or CI job can gate on it:

| Exit code | Meaning                                                     |
| --------- | ----------------------------------------------------------- |
| `0`       | The verdict is `passed`.                                    |
| `1`       | The verdict is `failed`.                                    |
| `2`       | The run ended without a verdict, including a cancelled run. |
| `3`       | An API or usage error.                                      |

Without `--wait`, `0` means the API accepted the request. Pressing Ctrl-C while waiting stops the wait and leaves the run going. The CLI prints the `eval cancel` command to stop it.

## Run an eval with the API

The API takes the scenario files in the request body, so you can call it from any language. Authenticate with a [personal access token](/pipecat-cloud/guides/personal-access-tokens) or the CLI's OAuth token as a Bearer token. The routes sit under your organization and agent:

```text
https://api.pipecat.daily.co/v1/organizations/{organization}/services/{agent}/eval-runs
```

<Steps>
  <Step title="Create a run">
    `files` maps each path to its UTF-8 text. `scenarioPath` is one of those
    paths, and `scenarioName` names the scenario within it.

    ```shell
    curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs" \
      -H "Authorization: Bearer $PIPECAT_TOKEN" \
      -H "Content-Type: application/json; charset=utf-8" \
      -d "$(jq -n --rawfile scenario scenarios/greeting.yaml '{
        kind: "synthetic",
        files: {"greeting.yaml": $scenario},
        scenarioPath: "greeting.yaml",
        scenarioName: "capital_question"
      }')"
    ```

    The API answers `202` with the run, in status `queued`, and a `Location`
    header with its URL.

  </Step>
  <Step title="Poll the run">
    Read the run until its `result` is set. While the run is live, the
    `Retry-After` header says when to ask again.

    ```shell
    curl "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs/$RUN_ID" \
      -H "Authorization: Bearer $PIPECAT_TOKEN"
    ```

  </Step>
</Steps>

A session run sets `kind` to `session` and adds the `sessionId`:

```shell
curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs" \
  -H "Authorization: Bearer $PIPECAT_TOKEN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d "$(jq -n --rawfile scenario scenarios/book_table.yaml --arg session "$SESSION_ID" '{
    kind: "session",
    sessionId: $session,
    files: {"book_table.yaml": $scenario},
    scenarioPath: "book_table.yaml",
    scenarioName: "judged"
  }')"
```

List an agent's runs, newest first, and cancel one:

```shell
curl "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs?limit=10&offset=0" \
  -H "Authorization: Bearer $PIPECAT_TOKEN"

curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs/$RUN_ID/cancel" \
  -H "Authorization: Bearer $PIPECAT_TOKEN"
```

### Request fields

| Field             | Description                                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`            | `synthetic` (the default) or `session`.                                                                                                                                     |
| `files`           | Required. Every file the scenario may include, keyed by path relative to the bundle's root, with UTF-8 text values.                                                         |
| `scenarioPath`    | Required. The scenario file: one of the keys of `files`.                                                                                                                    |
| `scenarioName`    | Required. The scenario's name within its file.                                                                                                                              |
| `sessionId`       | Required for a session run: an ended session of this agent. Not allowed on a synthetic run.                                                                                 |
| `params`          | Synthetic runs only: `connectTimeoutSeconds` (up to 120), `botReadyTimeoutSeconds` (up to 300), and `defaultTimeoutMs` (up to 600000, how long a turn waits for the agent). |
| `deadlineSeconds` | How long the run may take from its creation, queueing included. See [Limits](#limits).                                                                                      |

The [REST reference](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-run-create) lists every response and error.

### Cancel a run

Cancelling is a request that the run stops as soon as it can.

- A `queued` run ends at once as `cancelled`, and the API answers `200` with the run.
- A `running` run answers `202` with the run, still `running`. It ends as `cancelled` shortly after. A session that has already started stays started.
- Cancelling a run that is already `cancelled` answers `200`, so repeating a cancel is safe.
- Cancelling a run that ended any other way answers `409`.

## Read the result

A run has these fields:

| Field                                                  | Description                                                             |
| ------------------------------------------------------ | ----------------------------------------------------------------------- |
| `id`, `kind`, `scenarioPath`, `scenarioName`, `params` | What was requested.                                                     |
| `status`                                               | Where the run is. See [Statuses](#statuses).                            |
| `verdict`                                              | `passed`, `failed`, or `null` when the run ended without one.           |
| `sessionId`                                            | The session the run talked to, or for a session run, the one it judged. |
| `createdAt`, `startedAt`, `finishedAt`, `deadlineAt`   | Timestamps. `startedAt` is when a worker first took the run up.         |
| `result`                                               | `null` while the run is live. Otherwise the result below.               |

`result` holds:

- `reason`: why the run got its verdict, or why it has none. A failed run says what fell short, such as `The agent fell short on the metric 'politeness', scoring 0.50 where it needs 1.00: ...`.
- `metrics`: each metric's `name`, `score`, `passed` and `reason`.
- `details`: `kind` (`script` or `simulation`), `turns` with the checks on each, `failures`, and a simulation's `goal` with the judge's verdict on `success:`. `null` when the result was too large to keep.
- `conversation`: the conversation in Pipecat's format.
- `ignored` and `ignoredTotal`: the scenario's keys that had no effect (the first 20), and how many there were in all.
- `truncated`: `true` when the result was too large, in which case the conversation, details, and metric reasons are left out.

A finished run of the greeting scenario:

```json
{
  "id": "0b6b3c8e-5f4a-4a58-9a77-52f7c0f2e8d1",
  "kind": "synthetic",
  "status": "completed",
  "verdict": "passed",
  "scenarioPath": "greeting.yaml",
  "scenarioName": "capital_question",
  "sessionId": "5d9c2a1e-3f0b-4b6e-8d11-7a4e6c9b0f22",
  "createdAt": "2026-11-07T10:00:00.000Z",
  "startedAt": "2026-11-07T10:00:02.000Z",
  "finishedAt": "2026-11-07T10:00:21.000Z",
  "deadlineAt": "2026-11-07T10:30:00.000Z",
  "result": {
    "reason": "The agent passed the scenario.",
    "metrics": [],
    "details": {
      "kind": "script",
      "turns": ["..."],
      "failures": [],
      "goal": null
    },
    "conversation": ["..."],
    "ignored": [],
    "ignoredTotal": 0,
    "truncated": false
  }
}
```

### Statuses

A run is live while it is `queued`, `starting`, or `running`. It ends in one of:

| Status               | Meaning                                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `completed`          | The run reached a verdict, `passed` or `failed`.                                                               |
| `refused`            | The scenario can't run, or a session run's conversation is too long to judge. `result.reason` says why.        |
| `target_unavailable` | The agent never connected.                                                                                     |
| `not_started`        | A session run's session published no conversation, or none with its content. `result.reason` says what to do.  |
| `spend_limited`      | The organization's [spend limit](/api-reference/cli/cloud/spend-limit) was reached, so no session could start. |
| `expired`            | The run's deadline passed before it finished.                                                                  |
| `cancelled`          | The run was cancelled.                                                                                         |
| `timed_out`          | The run took longer than an eval may.                                                                          |
| `error`, `abandoned` | The run failed without a verdict. `abandoned` is a run that failed on every attempt.                           |

Every status except `completed` has a `null` verdict.

## Limits

| Limit                  | Value                                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Files in a run         | 256 KiB of UTF-8 in all, and at most 3.5 MiB as JSON with paths counted. The request body is at most 3 MiB. Paths are at most 1024 characters. |
| Synthetic run deadline | `deadlineSeconds` from 90 to 7200. 1800 (30 minutes) by default.                                                                               |
| Session run deadline   | `deadlineSeconds` from 240 to 1800. 600 (10 minutes) by default.                                                                               |
| Conversation judged    | 256,000 characters or 2,000 messages. A longer one is `refused`.                                                                               |
| Scenario name          | 256 characters.                                                                                                                                |

The deadline counts from the run's creation, including time spent waiting for the agent to have room. A run still going at its deadline ends as `expired`.

Evals are not on for every deployment. Where they aren't, every route answers `503` with the code `EVALS-NOT-AVAILABLE`.
