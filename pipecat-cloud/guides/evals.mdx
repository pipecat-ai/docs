An eval run checks a deployed agent against a [Pipecat eval scenario](/pipecat/evals/overview) without you hosting the harness. You send a scenario, Pipecat Cloud runs it, and you read back a verdict, the reasons for it, the metrics, and the conversation. A [suite run](#run-a-suite) runs many scenarios, or one scenario many times, and reports on them together.

<Warning>
  A synthetic eval run, and every member of a suite run, starts real sessions of
  your deployed agent, and the agent calls its real tools: bookings, emails,
  payments, database writes. Run evals against an agent that uses test
  credentials or against a staging deployment, never against an agent wired to
  production systems. A session run starts no session and calls no tools.
</Warning>

## Run Kinds

| Kind        | What it does                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `synthetic` | A simulated caller, or the scripted turns of the scenario, holds a conversation with a new session of your deployed agent. The default.                                                          |
| `session`   | Judges a session of the agent that has already ended, using `success:` and `criterion:` metrics. It starts no session. Needs [conversation publishing](#publish-conversations-for-session-runs). |

Synthetic runs take scenario files in the [`pipecat eval`](/api-reference/cli/eval) format. Session runs take [judging criteria](#session-criteria). Both end with a verdict of `passed`, `failed` or `skipped` when they can reach one. [Audio scenarios](#audio-scenarios) run only where the agent's [capabilities](#check-what-is-available) list `synthetic.audio` as `available`; elsewhere they are refused.

## Write a Scenario

A scenario file is a YAML file in the [format described in the Pipecat evals docs](/pipecat/evals/scenario-configuration). A run sends the scenario file and the files it includes with `!include`, and nothing else.

### A Synthetic Scenario

`scenarios/greeting.yaml` is a [scripted scenario](/pipecat/evals/scripted-scenarios) that checks the agent's reply to one question:

```yaml scenarios/greeting.yaml
name: greeting

scenarios:
  - name: capital_question
    turns:
      - user: "What is the capital of France?"
        expect:
          - event: response
            eval: "the response says the capital of France is Paris"
```

A [simulated scenario](/pipecat/evals/simulated-scenarios) works the same way. An LLM plays the caller, and the judge decides `success:` once the call is over.

### Included Files

A scenario can pull in other YAML files with `!include`. On Pipecat Cloud, a nested include resolves relative to the file that names it, and every included file must be inside the root the run is built from.

Pipecat's own examples include files with paths like `!include ../judge_text.yaml`, which leave the scenario's directory. Set `--root` to the directory they share. With `scenarios/simulated/book_table.yaml` including `../judge_text.yaml`:

```shell
pipecat cloud eval run my-agent scenarios/simulated/book_table.yaml --root scenarios
```

The run then carries `simulated/book_table.yaml` and `judge_text.yaml`. With the API, the keys of `files` are those root-relative paths.

### Session Criteria

A session run judges a conversation that already happened. Its criteria require a nonempty `success:` and can include judged metrics with `criterion:`. The file uses the same named `scenarios:` entries as a scenario file, without requiring `persona:` or `goal:`. The CLI's `eval judge` takes a file with exactly one named entry.

Use only judged metrics (`criterion:`) on a session run. A `measure:` metric, `function_calls` included, is refused, and the API answers `400`.

```yaml criteria/book_table.yaml
name: book_table

scenarios:
  - name: judged
    success: "the bot confirmed a reservation for two at 6 PM (a booking tool was called)"

    metrics:
      - name: politeness
        criterion: "the reply is courteous, never curt or dismissive"
        min_score: 1
      - name: confirms_booking
        criterion: "when the caller has given a name and a time, the reply confirms the booking details"
        min_score: 0.8
```

See [Metrics](/pipecat/evals/simulated-scenarios#metrics) for how a judged metric is scored.

The `result.ignored` field of a finished run lists the scenario's keys that had no effect, the first 20 of them. `result.ignoredTotal` counts them all.

## Audio Scenarios

An [audio scenario](/pipecat/evals/scenario-configuration#text-and-audio-modes) speaks the caller's turns to the agent, judges the agent's spoken audio, or both. Before the conversation starts, an audio run checks the audio settings the agent reports in its `bot-ready` message. When the agent's eval transport has audio turned off in a direction the scenario uses, the run ends `error`, without a verdict or a conversation. Its failure kind is `audio_unsupported`, and `result.reason` says to turn on `audio_in_enabled` (the caller's audio) or `audio_out_enabled` (the agent's) in the eval transport's params: the one for each direction your scenario uses. Running it again gives the same answer until you change the agent.

An agent on `pipecat-ai` before 1.13 reports no audio settings, so its audio runs go unchecked: if the audio doesn't get through, the run fails or ends without a verdict on its own terms.

## Publish Conversations for Session Runs

A session run needs the session's conversation, and an agent doesn't publish it by default. To publish it, set `PCC_EVAL_CONVERSATIONS=true` in the agent's environment, for example in its [secret set](/pipecat-cloud/fundamentals/secrets):

```shell
pipecat cloud secrets set my-secrets PCC_EVAL_CONVERSATIONS=true
```

Publishing needs:

- The Pipecat Cloud base image `0.2.12` or later.
- `pipecat-ai` 1.13 or later in the agent.

Then redeploy the agent. Only sessions that start afterwards publish a conversation. The published conversation includes what the caller and the agent said and the agent's tool calls with their arguments.

- A session whose process is killed, by a crash or a forced stop, publishes nothing.
- With `PCC_WITHHOLD_CONTENT=true`, the agent publishes no conversation, and a session run ends `not_started`.
- Publishing stops 10 seconds after the session ends, so a long conversation can be published only in part. A session run on it ends `error`.
- A session run on a session that hasn't ended is refused with `409`.

Synthetic runs don't need this setting.

## What Is Sent to OpenAI

Hosted simulated callers and LLM judges use OpenAI models on Daily's account with zero data retention:

- **A simulated synthetic run** sends the scenario and conversation with your agent to the simulated caller and judge.
- **A scripted synthetic run** uses a hosted judge only for `eval:` expectations. A script with only mechanical checks, such as `text_contains:`, uses no hosted OpenAI models.
- **A session run** sends the whole conversation your agent published and the scenario's criteria to the judge.

The conversation includes the tool calls the agent made and their arguments. During a synthetic run, your agent still uses its own configured services.

Eval runs aren't available to organizations with HIPAA controls. Creating one is refused with `403`: `Hosted evals aren't available for organizations with HIPAA controls.` Controls are checked again before a synthetic session or a session judge starts. Enabling controls prevents further starts; evaluations already in progress continue. You can still read, list and cancel runs.

For a session run, enable [conversation publishing](#publish-conversations-for-session-runs) only for agents whose conversations you're willing to send.

## Check What Is Available

Two read-only routes say what you can run. Both answer even when hosted evals are off, and neither starts a session:

- [Get eval capabilities](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-capabilities-get), for the organization: `enabled`; `creation`, whether the organization may create runs and publish bundles, with a `reason` and `message` when it may not; `bundles`, whether it can [store bundles](#store-files-as-a-bundle); and `suites`, whether it can [run suites](#run-a-suite).
- [Get an agent's eval capabilities](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-capabilities-agent-get), for one agent: `synthetic`, `synthetic.audio` and `session`, each with a `state` of `available`, `unavailable` or `unknown`, and a `reason` and `message` when it isn't available.

```json eval-capabilities.json
{
  "enabled": true,
  "creation": {
    "allowed": true,
    "reason": null,
    "message": null
  },
  "bundles": true,
  "suites": true
}
```

The answers are advisory: a run is still checked when you create it. A suite run of inline files needs both `suites` and `bundles`.

## Run an Eval with the CLI

The commands live under `pipecat cloud eval`. They need an authenticated CLI ([`pipecat cloud auth login`](/api-reference/cli/cloud/auth), or a [personal access token](/pipecat-cloud/guides/personal-access-tokens)). See the [command reference](/api-reference/cli/cloud/eval) for every option.

Run a scenario file and wait for the verdict:

```shell
pipecat cloud eval run my-agent scenarios/greeting.yaml --scenario capital_question
```

Where the organization has suite runs and bundles ([capabilities](#check-what-is-available)), and you give no `--param`, `run` runs the selected scenarios as one [suite run](#run-a-suite), with one verdict. Otherwise each scenario is a run of its own, side by side.

Judge a session that has ended:

```shell
pipecat cloud eval judge my-agent 3b1f0f6e-7c1a-4e0e-9d47-0f4a5f0a9a11 --criteria criteria/book_table.yaml
```

Pass several session IDs to `judge` to apply the same criteria to each session. Both `run` and `judge` wait for verdicts by default. Use `--no-wait` to submit and return, or `-v` to include the conversation and the checks or judgments that decided each result. Check on a run, list recent runs, or cancel one:

```shell
pipecat cloud eval status RUN_ID --agent my-agent --wait
pipecat cloud eval list my-agent
pipecat cloud eval cancel RUN_ID --agent my-agent
```

When a command waits, its exit code says how the runs came out, so a script or CI job can gate on it: `0` for `passed` or `skipped`, or a completed measurement; `1` for `failed`; `2` for a run or suite run that ended without a verdict; `3` for an API or usage error; and `130` when you press Ctrl-C, which leaves the runs going. See the [exit codes](/api-reference/cli/cloud/eval#exit-codes).

Without `--scenario`, `run` selects every script and simulation in the file, and leaves out entries with criteria alone, which are for `judge`. Repeat `--scenario` to select several. The CLI sends the scenario or criteria file and the files it includes under `--root` (the file's directory by default), and refuses hidden files, key and certificate files, `*.env` files, symlinks that leave the root, and files that aren't UTF-8, before it sends anything. See [the files a run sends](/api-reference/cli/cloud/eval#the-files-a-run-sends).

## Run an Eval with the API

The API takes the scenario files in the request body, or names a [stored revision](#run-from-a-stored-revision), so you can call it from any language. Authenticate with a [personal access token](/pipecat-cloud/guides/personal-access-tokens) or the CLI's OAuth token as a Bearer token. The routes sit under your organization and agent:

```text
https://api.pipecat.daily.co/v1/organizations/{organization}/services/{agent}/eval-runs
```

<Steps>
  <Step title="Create a run">
    `files` maps each path to its UTF-8 text. `scenarioPath` is one of those
    paths, and `scenarioName` names the scenario within it.

    ```shell
    curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs" \
      -H "Authorization: Bearer $PIPECAT_TOKEN" \
      -H "Content-Type: application/json; charset=utf-8" \
      -d "$(jq -n --rawfile scenario scenarios/greeting.yaml '{
        kind: "synthetic",
        files: {"greeting.yaml": $scenario},
        scenarioPath: "greeting.yaml",
        scenarioName: "capital_question"
      }')"
    ```

    The API answers `202` with the run, in status `queued`, and a `Location`
    header with its URL.

  </Step>
  <Step title="Poll the run">
    Read the run until its `result` is set. While the run is live, the
    `Retry-After` header says when to ask again.

    ```shell
    curl "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs/$RUN_ID" \
      -H "Authorization: Bearer $PIPECAT_TOKEN"
    ```

  </Step>
</Steps>

A session run sets `kind` to `session` and adds the `sessionId`:

```shell
curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs" \
  -H "Authorization: Bearer $PIPECAT_TOKEN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d "$(jq -n --rawfile scenario criteria/book_table.yaml --arg session "$SESSION_ID" '{
    kind: "session",
    sessionId: $session,
    files: {"book_table.yaml": $scenario},
    scenarioPath: "book_table.yaml",
    scenarioName: "judged"
  }')"
```

List an agent's runs, newest first, and cancel one:

```shell
curl "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs?limit=10&offset=0" \
  -H "Authorization: Bearer $PIPECAT_TOKEN"

curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs/$RUN_ID/cancel" \
  -H "Authorization: Bearer $PIPECAT_TOKEN"
```

The list takes `kind`, `status`, `verdict` and `suiteRunId` filters.

### Request Fields

| Field              | Description                                                                                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`             | `synthetic` (the default) or `session`.                                                                                                                                     |
| `files`            | Every file the scenario may include, keyed by path relative to the bundle's root, with UTF-8 text values. Required unless the run names `bundleRevisionId`.                 |
| `bundleRevisionId` | A [stored revision](#run-from-a-stored-revision) whose files the run runs, in place of `files`. Needs `requestId`.                                                          |
| `requestId`        | With `bundleRevisionId`: a UUID you generate, sent again unchanged when you retry the request.                                                                              |
| `scenarioPath`     | Required. The scenario file: one of the run's files.                                                                                                                        |
| `scenarioName`     | Required. The scenario's name within its file.                                                                                                                              |
| `sessionId`        | Required for a session run: an ended session of this agent. Not allowed on a synthetic run.                                                                                 |
| `params`           | Synthetic runs only: `connectTimeoutSeconds` (up to 120), `botReadyTimeoutSeconds` (up to 300), and `defaultTimeoutMs` (up to 600000, how long a turn waits for the agent). |
| `deadlineSeconds`  | How long the run may take from its creation, queueing included. See [Limits](#limits).                                                                                      |

The [REST reference](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-run-create) lists every response and error.

### Cancel a Run

Send the POST with no body, or send `{}` with `Content-Type: application/json`. Other body shapes are a `400`. An oversized JSON or form body is a `413`; an unsupported charset or `Content-Encoding` is a `415`. A successful cancel returns `200` with the run's current state: the cancellation request was recorded, or the run was already cancelled. It sends no `Retry-After` or `Location` header.

- A `queued` run ends at once as `cancelled`.
- An active run may still be `starting` or `running` in the response. No further cancel request is needed. You can optionally GET the run to check its eventual outcome.
- A run that reaches its own end before the cancel does keeps that end.
- Cancelling a run that is already `cancelled` is safe.
- Cancelling a run that ended any other way answers `409`: `The run has already finished.`

Stopping an active evaluation is best effort. The `cancelled` status does not confirm that all evaluation activity has stopped. If stopping could not be confirmed, `result.reason` says the evaluation may continue until its deadline. Cancellation does not undo usage already incurred by an agent session. Cancelling works while the organization is suspended.

## Store Files as a Bundle

A **bundle** is a named set of scenario, suite and included files that your organization keeps. Each time you publish its files, they become a new **revision**: numbered from 1, never changed afterwards, and checked before they are stored. Runs and suite runs name a revision by its ID, so the files a run ran stay readable.

Publish a directory with the CLI. The first push creates the bundle, and each later push publishes its next revision:

```shell
pipecat cloud eval bundle push support-evals evals/
```

The CLI shows the files and asks you to confirm, then prints the revision's number and what it holds. With the API, [create the bundle](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-bundle-create) with its first files, then [publish a revision](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-bundle-revision-create) for each change. Both take a `requestId`, a UUID you generate: a retry that sends the same request with the same `requestId` creates nothing more, and answers with what the first one made.

The check classifies every file:

- A `.yaml` or `.yml` mapping with `kind: suite` is a [suite file](#the-suite-file).
- A file that a suite entry names in `runner_body: {path: ...}` is a body.
- A `.yaml` or `.yml` mapping with a `name:` is a scenario file. Each of its scenarios is a `script` (it has `turns:`), a `simulation` (it has `persona:`), or a `rubric` (only `success:` and judged metrics, for session runs).
- Any other file must be included by a scenario file. A file that nothing uses is refused.

A refused bundle stores nothing: the `400` lists the first 50 problems in `problems`, each with its `file`, the `scenario` and `field` within it where it has them, a `code` and a `message`, and `total` counts them all. A stored revision's `catalog` lists what its files hold, and its `coverage` says how far the check went. With `structural` coverage, a scenario that Pipecat's loader would refuse can still be stored, and is refused when a run uses it.

[Get an eval bundle revision](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-bundle-revision-get) reads a revision's files back. [Deleting a bundle](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-bundle-delete) takes it off the list and frees its name. No new run can name its revisions, but the revisions that runs already name stay readable.

### Run from a Stored Revision

An eval run can name a stored revision instead of sending files. Set `bundleRevisionId` and a `requestId` in place of `files`:

```shell
curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-runs" \
  -H "Authorization: Bearer $PIPECAT_TOKEN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d "$(jq -n --arg revision "$REVISION_ID" --arg request "$(uuidgen)" '{
    requestId: $request,
    bundleRevisionId: $revision,
    scenarioPath: "scenarios/greeting.yaml",
    scenarioName: "capital_question"
  }')"
```

Sending the same request again with the same `requestId` answers `202` with the run it made, as it is now, and the header `Idempotent-Replayed: true`. The same `requestId` with a different request is a `409`, and so is a revision whose bundle has been deleted.

A run of inline `files` keeps them too, as an **anonymous revision** that only that run names. The run's `bundleRevisionId` reads them back; an anonymous revision has no bundle, number or catalog.

## Run a Suite

A **suite run** runs a set of scenarios against one agent and reports on them together. Each planned run of a scenario is a **member**: an eval run of its own, with its own result. A suite run's plan is fixed when it is accepted: every member, with its entry, scenario and attempt.

### The Suite File

A suite file is a YAML file with `kind: suite`, stored in a bundle beside the scenarios it names. It uses the words of the [`pipecat eval suite` manifest](/pipecat/evals/suites), without those that start agents locally, since the suite run names its agent:

```yaml suite.yaml
kind: suite
schemaVersion: 1
concurrency: 2
suite:
  - name: baseline
    scenarios:
      - scenarios/greeting.yaml
      - { path: scenarios/simulated/book_table.yaml, name: available }
  - name: vip-caller
    runner_body:
      data: { tier: vip }
    scenarios:
      - { path: scenarios/simulated/book_table.yaml, name: available }
```

| Key             | Description                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| `kind`          | Required: `suite`.                                                                                    |
| `schemaVersion` | Required: `1`.                                                                                        |
| `suite`         | Required: the entries, at least one.                                                                  |
| `concurrency`   | How many members run at once. See [Concurrency and Deadlines](#concurrency-and-deadlines).            |
| `repeat`        | How many times every selected scenario runs. See [Repeat and Measurements](#repeat-and-measurements). |

Each entry takes:

| Key           | Description                                                                                                                                                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scenarios`   | Required. Each item is a scenario file's path in the bundle, which selects every scenario it holds except rubrics, or `{path, name}`, which selects one scenario.                                                                                                |
| `name`        | The entry's label, which its members and pass rates carry. Entries without one share the empty label, so they can't select the same scenario.                                                                                                                    |
| `runner_body` | A session body for the entry's members, as a [`/start` request](/pipecat-cloud/guides/websocket-authentication) would send it: `{path: <file>}`, a YAML or JSON file in the bundle, or `{data: {...}}`. Needs an agent deployed with `websocket_auth = "token"`. |
| `concurrency` | At most this many of the entry's members at once.                                                                                                                                                                                                                |

Suite files take no `!include`. The manifest's keys for starting agents, such as `bot:`, `spawn:` and `runs_dir:`, are refused.

### Start a Suite Run

With the CLI, run a suite file from a stored bundle's latest revision, or from revision 3 with `--bundle support-evals@3`:

```shell
pipecat cloud eval suite run my-agent --bundle support-evals --suite suite.yaml
```

`pipecat cloud eval run` also runs a scenario file from your machine as a suite run, where the organization has suite runs and bundles ([capabilities](#check-what-is-available)).

With the API, [create a suite run](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-suite-run-create):

```shell
curl -X POST "https://api.pipecat.daily.co/v1/organizations/$ORG/services/my-agent/eval-suite-runs" \
  -H "Authorization: Bearer $PIPECAT_TOKEN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d "$(jq -n --arg revision "$REVISION_ID" --arg request "$(uuidgen)" '{
    requestId: $request,
    bundleRevisionId: $revision,
    suitePath: "suite.yaml"
  }')"
```

| Field                         | Description                                                                                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `requestId`                   | Required. A UUID you generate, sent again unchanged when you retry the request.                                                                                                                              |
| `bundleRevisionId` or `files` | Exactly one: a stored revision, or the files inline, which are checked as a bundle and kept as an anonymous revision.                                                                                        |
| `suitePath` or `scenarioPath` | Exactly one: a suite file, or a scenario file to run as a suite of one entry. With `scenarioPath`, `scenarioNames` runs only the scenarios it lists, in its order.                                           |
| `filters`                     | Narrows the plan: `kinds` (`script`, `simulation`) and `scenarios` (`{path, name}`, each one the plan selects), applied before repetition. Filters that leave nothing to run are refused as an `empty_plan`. |
| `repeat`, `concurrency`       | Replace the suite file's `repeat:` and `concurrency:`.                                                                                                                                                       |
| `deadlineSeconds`             | From 90 to 43200 (12 hours). 43200 by default.                                                                                                                                                               |

The API answers `202` with the suite run, its `entries` and `counts.planned`, and a `Location` header. Its `target` says what it runs: `{"kind": "suite", "suitePath": ...}` for a suite file, or `{"kind": "scenarios", "scenarioPath": ..., "scenarioNames": [...]}` for a scenario file, such as the one `eval run` sends, with `scenarioNames` only when the request listed them. Nothing is recorded unless the answer is `202`, and a retry with the same `requestId` answers with the suite run the first request made. A plan that can't be made is refused with `400` and a `refusal` that names why, such as an unknown suite file or a scenario named twice. While the agent is between deployments, a new suite run is refused with `409` (`EVAL-AGENT-BETWEEN-DEPLOYMENTS`): retry once the deployment has completed.

### Repeat and Measurements

Without `repeat`, every scenario runs once, except a simulation, which runs its own `runs:`, and every run counts toward the verdict. With `repeat`, from the request or the suite file, every selected scenario runs that many times instead, replacing a simulation's `runs:`. Members run attempt by attempt: every scenario's first attempt in entry order, then every second, and so on.

Above 1, the suite run is a **measurement** (`measurement: true`). It has no verdict, and reports a pass rate for each entry and scenario in `passRates`: `passed / (passed + failed + skipped)`, or null until one of its members has passed, failed or been skipped. Members that ended without a verdict are counted apart, in `withoutVerdict`, and never in a rate. Pass rates are only on [Get an eval suite run](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-suite-run-get); lists show `passRates: null`. The threshold is yours to choose.

### Concurrency and Deadlines

`concurrency` caps how many members run at once: the request's, otherwise the suite file's, otherwise 4, as in Pipecat's manifests. The API sets the most. An entry's own `concurrency:` caps that entry. The suite run's `concurrency.effective` shows what applies. Members also wait for room on the agent, up to its [maximum agents](/pipecat-cloud/fundamentals/scaling#maximum-agents) less its other sessions, and suite runs on one agent share that room fairly.

A suite run's deadline covers all of it, queueing and every member, from when it is accepted: 12 hours, unless `deadlineSeconds` sets it shorter. Each member also has a single run's own deadline, cut short to the suite run's.

### Read a Suite Run

Poll [Get an eval suite run](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-suite-run-get) until it has ended. While it is live, the `Retry-After` header says when to ask again. With the CLI:

```shell
pipecat cloud eval suite status SUITE_RUN_ID --wait
```

| Status      | Meaning                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------- |
| `queued`    | Accepted. No member has been admitted yet.                                                              |
| `running`   | At least one member has been admitted.                                                                  |
| `completed` | Every member was admitted and has ended.                                                                |
| `cancelled` | A cancel stopped it.                                                                                    |
| `expired`   | Its deadline stopped it.                                                                                |
| `error`     | It couldn't go on as accepted. `error` says why: see [What Stops a Suite Run](#what-stops-a-suite-run). |

A member's own failure stays on the member: it never ends the suite run as `error`.

`counts` places every member. `pending` (not yet admitted), `live` and `terminal` add up to `planned`; `passed`, `failed`, `skipped` and `withoutVerdict` add up to `terminal`. Once a suite run has stopped, members never admitted count as terminal, without a verdict.

A suite run has a verdict only once it has `completed`, and never as a measurement:

| Its members                                              | `verdict` |
| -------------------------------------------------------- | --------- |
| Any failed                                               | `failed`  |
| None failed, and any ended without a verdict             | `null`    |
| Every one passed or was skipped, and at least one passed | `passed`  |
| Every one was skipped                                    | `skipped` |

A completed measurement, with `repeat` 40 over one entry that runs the two scenarios of `greet.yaml`:

### Cancel a Suite Run

```shell
pipecat cloud eval suite cancel SUITE_RUN_ID
```

With the API, POST to [the suite run's `cancel`](/api-reference/pipecat-cloud/rest-reference/endpoint/eval-suite-run-cancel) with no body. Once the request is recorded, no more members are admitted, members not yet admitted never run, and live members are cancelled as a [cancelled run](#cancel-a-run) is. The response can still show `running` while they finish, and results they reach first are kept. While it's live, the answer has a `Retry-After` header. The suite run then ends `cancelled`, unless something had already stopped it, such as its deadline. Cancelling again is safe. Cancelling a suite run that already ended another way answers `409`.

### What Stops a Suite Run

| Cause                                                                                                                                                | Ends as                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| A cancel.                                                                                                                                            | `cancelled`                                       |
| Its deadline passes with members waiting or live, or too little time is left for the next member to start.                                           | `expired`                                         |
| The agent is redeployed: its active deployment changes, or a member's session runs on a deployment other than the one the suite run was accepted on. | `error`, with `error.code` `deployment_changed`   |
| Which deployment a member's session ran on can't be confirmed.                                                                                       | `error`, with `error.code` `deployment_unknown`   |
| Its bundle revision is no longer available.                                                                                                          | `error`, with `error.code` `revision_unavailable` |

The first cause stands, and a later one never replaces it. From then on the suite run admits no members, and it ends once none is live. A suite run's members are held to the deployment the agent was on when it was accepted, so a redeploy ends the suite run rather than mixing versions of your agent, and a suite run [can't start](#start-a-suite-run) while a deployment is in progress. `deployment_changed` names both deployments in `error.expectedDeploymentId` and `error.deploymentId`.

### Judging Versions

Every eval run records its **judging version** in `executor.fingerprint`: an identifier of everything that decides a verdict. A suite run holds its members to one judging version, its own `fingerprint`, taken from the first member to report one.

If the platform's judging changes during a suite run, members keep being judged by the suite run's version where they can. A member that can't be judged by it in time is judged by the newer version, and the suite run is flagged `mixed: true`. A mixed suite run keeps its verdict. A mixed measurement's pass rates are split by version: each `passRates` row then has its `fingerprint`. `pipecat cloud eval suite status` shows the judging version, and warns when a suite run is mixed.

## Read the Result

A run has these fields:

| Field                                                  | Description                                                                                                                            |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `kind`, `scenarioPath`, `scenarioName`, `params` | What was requested.                                                                                                                    |
| `serviceName`                                          | The agent. `environmentName` and `parentServiceName` are set when the agent is an environment of another.                              |
| `status`                                               | Where the run is. See [Statuses](#statuses).                                                                                           |
| `verdict`                                              | `passed`, `failed`, `skipped`, or `null` when the run ended without one.                                                               |
| `bundleRevisionId`                                     | The revision whose files the run ran: a [stored one](#run-from-a-stored-revision), or the anonymous one its inline files were kept as. |
| `suiteRunId`, `suiteMemberOrdinal`                     | The [suite run](#run-a-suite) the run is a member of, and its place in the plan. Both null for a run of its own.                       |
| `executor`                                             | The [judging version](#judging-versions) (`fingerprint`) and build that ran the run. Null until they are reported.                     |
| `sessionId`                                            | The associated agent session, if known. For a session run, the session it judges.                                                      |
| `createdAt`, `startedAt`, `finishedAt`, `deadlineAt`   | Timestamps. `startedAt` is when the run first left the queue.                                                                          |
| `result`                                               | `null` while the run is live. Otherwise the result below.                                                                              |

`result` holds:

- `reason`: why the run got its verdict, or why it has none. A failed run says what fell short, such as `The agent fell short on the metric 'politeness', scoring 0.50 where it needs 1.00: ...`.
- `metrics`: each metric's `name`, `score`, `passed` and `reason`.
- `details`: `kind` (`script` or `simulation`), `turns` with the checks on each, `failures`, and a simulation's `goal` with the judge's verdict on `success:`. `null` when the result was too large to keep.
- `conversation`: the conversation in Pipecat's format. A scripted run's can be `[]`.
- `ignored` and `ignoredTotal`: the scenario's keys that had no effect (the first 20), and how many there were in all.
- `truncated`: `true` when the result was too large, in which case the conversation, details, and metric reasons are left out.

### Statuses

A run is live while it is `queued`, `starting`, or `running`. It ends in one of:

| Status               | Meaning                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `completed`          | The run reached a verdict, `passed`, `failed` or `skipped`.                                                                     |
| `refused`            | The scenario can't run, or a session run's conversation is too long to judge. `result.reason` says why.                         |
| `target_unavailable` | The agent never connected.                                                                                                      |
| `not_started`        | The run could not start or continue. `result.reason` says why, such as HIPAA controls or a missing conversation.                |
| `spend_limited`      | The organization's [spend limit](/api-reference/cli/cloud/spend-limit) was reached, preventing further session or judge starts. |
| `expired`            | The run's deadline passed before it finished.                                                                                   |
| `cancelled`          | The run was cancelled. `result.reason` explains what may have started and any unconfirmed stop.                                 |
| `timed_out`          | The eval itself ran past its [time limit](#limits).                                                                             |
| `error`, `abandoned` | The run failed without a verdict. `abandoned` is a run that failed on every attempt.                                            |

Every status except `completed` has a `null` verdict.

## Limits

| Limit                  | Value                                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Files in a run         | 256 KiB of UTF-8 in all, and at most 3.5 MiB as JSON with paths counted. The request body is at most 3 MiB. Paths are at most 1024 characters. |
| Files in a bundle      | 2,000 files and 256 KiB of UTF-8 in all, and at most 3.5 MiB as JSON with paths counted. Paths are at most 1024 characters.                    |
| Bundle name            | 1 to 128 lowercase letters, digits, dots, dashes and underscores, starting and ending with a letter or a digit.                                |
| Synthetic run deadline | `deadlineSeconds` from 90 to 7200. 1800 (30 minutes) by default.                                                                               |
| Session run deadline   | `deadlineSeconds` from 240 to 1800. 600 (10 minutes) by default.                                                                               |
| Suite run deadline     | `deadlineSeconds` from 90 to 43200. 43200 (12 hours) by default.                                                                               |
| Eval time limit        | The smaller of one hour and the deadline less 30 seconds. An eval still going then ends as `timed_out`.                                        |
| Scenario loading       | A scenario's includes load at most 200 files, 256 KiB and 20,000 values in all. An include counts each time it is named.                       |
| Conversation judged    | 256,000 characters or 2,000 messages. A longer one is `refused`.                                                                               |
| Scenario name          | 256 characters.                                                                                                                                |

The deadline counts from the run's creation, including time spent waiting for the agent to have room. A run still going at its deadline ends as `expired`. The eval itself is a part of that time, and has the limit above.

Hosted evals are not available in every region. Creating a run for an agent in a region without them is refused with `400`.
