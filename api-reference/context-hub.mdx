[Pipecat Context Hub](https://github.com/pipecat-ai/pipecat-context-hub) indexes Pipecat documentation, code examples, and framework API source into a local vector database on your machine. It's built for coding workflows: queries return the actual source and snippets your AI tool needs to write working code, not synthesized prose.

Pipecat's docs, examples, and API surface change often and span several repositories, so a model working from training data goes stale fast. The hub keeps a locally refreshed, version-aware index that you can query directly. Check `pipecat context-hub status` or `get_hub_status` before relying on its freshness or indexed framework version. You can also point it at your own repositories (public or private) to index private code alongside the framework.

Every tool runs two ways: as a one-shot CLI command and as an MCP server. Use the CLI for a quick lookup. Add the MCP server when a session needs repeated, exploratory queries.

## ChatGPT plugin

The [Pipecat Context Hub plugin](https://github.com/pipecat-ai/pipecat-context-hub/tree/main/plugins/pipecat-context-hub) is a skills-only ChatGPT plugin for exploring, building, and deploying voice and multimodal Pipecat agents. It provides Setup, Explore, Build, and Deploy workflows grounded in local Context Hub CLI queries.

The plugin is a wrapper around the Pipecat CLI and can be invoked from the ChatGPT desktop application. Installing the plugin adds its skills and branding assets. When onboarding is requested, Setup can install or reuse the Pipecat CLI, the Context Hub runtime, the Cloud extension, and a local index in the selected execution environment. It can also start Pipecat Cloud account and login setup; you approve the changes and complete browser authentication yourself. It does not install credentials or provision Cloud infrastructure. Some current Pipecat CLI distributions bundle Context Hub; otherwise Setup installs it alongside the CLI. Build and Deploy still require local command execution and, for Cloud workflows, an authenticated Pipecat Cloud environment. The CLI and MCP sections below describe the direct/manual setup path for other coding clients; they do not install or configure the ChatGPT plugin. The plugin uses Context Hub CLI queries and does not require MCP.

See the plugin [README](https://github.com/pipecat-ai/pipecat-context-hub/blob/main/plugins/pipecat-context-hub/README.md) and [changelog](https://github.com/pipecat-ai/pipecat-context-hub/blob/main/plugins/pipecat-context-hub/CHANGELOG.md) for packaging and release details.

After activating the plugin, the chat might ask **“Set up Pipecat Context Hub”**. The plugin
checks the local CLI and index, then uses grounded Context Hub queries for
Explore, Build, and Deploy.

All three surfaces can be explicitly installed, but only the ChatGPT plugin
can be surfaced inline by ChatGPT or Codex on the desktop app. The plugin may
be recommended while a user is discussing how to build an agent; CLI and MCP
are not inline recommendation surfaces.

| Surface        | Explicit installation                                                                                          | Inline recommendation in the ChatGPT/Codex desktop app |
| -------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| CLI            | Install `pipecat-ai[cli]` manually                                                                             | No                                                     |
| MCP            | Run `pipecat context-hub install` or register the server manually                                              | No                                                     |
| ChatGPT plugin | [Install Pipecat Context Hub in ChatGPT](https://chatgpt.com/plugins/plugins_6ac6b44c8d1881919f9dc3ffefbc6007) | Yes, host-controlled                                   |

### How the plugin helps agents write better Pipecat code

Pipecat documentation, examples, and framework APIs change frequently and span
multiple repositories. An agent relying only on model training data can suggest
stale imports, incorrect signatures, or examples that do not match the Pipecat
version in use. Context Hub gives the agent a local, source-grounded query path
for current guides, working examples, API definitions, targeted source snippets,
and deprecation status.

The plugin's normal workflow is:

1. **Setup** checks whether the host can run the required commands, whether
   Context Hub is installed, and whether a usable local index exists.
2. **Explore** retrieves relevant documentation, examples, and API details before
   making Pipecat-specific recommendations.
3. **Build** discovers the installed Pipecat CLI, validates the requested
   scaffold options, and creates or adapts an application after an explicit
   build request.
4. **Deploy** checks the application and Cloud target, prepares an exact
   deployment and secret-change proposal, and waits for approval before making
   deployment or secret mutations.

The agent should retrieve the relevant source before making framework-specific
API claims. Retrieval is evidence for implementation; it is not a substitute
for running tests or validating provider credentials.

The plugin reuses healthy installations and indexes. It does not silently
refresh an index, replace an installed CLI, upload credentials, or deploy an
application.

For example, a request to build a Daily bot with TTS and STT should lead the
agent to find the relevant concepts, example, API surface, and lifecycle status
before writing code:

```text
search_docs("Daily + TTS + STT")
search_examples("Daily TTS STT", domain="backend")
search_api("DailyTransport")
check_deprecation("PipelineTask")
```

<Note>
  Inline plugin surfacing, activation, and approval behaviour remain controlled
  by the host and the user. Explicit installation from the link above is
  separate from inline recommendation, and a recommendation is not guaranteed
  for every conversation. The plugin cannot change ChatGPT approval settings.
</Note>

<Note>
  This is a tool for *your* coding agent, not something your bot uses at
  runtime. For a bot that connects to MCP servers, see
  [`MCPClient`](/api-reference/server/utilities/mcp/mcp) and the
  `pipecat-ai[mcp]` extra.
</Note>

## Set up Context Hub for coding clients

The hub ships with the Pipecat CLI, so installing the CLI is the whole install:

```bash
uv tool install "pipecat-ai[cli]"
```

If you scaffold with [`pipecat init`](/api-reference/cli/init), setup is already done — it registers the MCP server with the coding agents it finds and offers to build the index. Otherwise, do both in one step:

```bash
pipecat context-hub install
```

`install` registers the MCP server with each coding agent CLI it finds, echoing each command it runs, then builds the index. Editors configured by hand — Cursor, VS Code, Zed — get the config block printed for you to paste instead; `install` exits `3` to say so, where `0` means a client was configured.

The first build takes upwards of three minutes and about 900 MB of disk: it clones the indexed repositories, downloads local embedding models, and embeds roughly 17,000 records. Later refreshes skip unchanged sources, so they usually take one to two minutes.

Every hub command is available as `pipecat context-hub <command>`; see the [`pipecat context-hub` reference](/api-reference/cli/context-hub) for the full flag surface.

If the index gets corrupted, force a rebuild:

```bash
pipecat context-hub refresh --force
```

By default `refresh` indexes framework source at the newest release tag, so results match a typical project. Pin it to target a specific older release, or pass `head` to track the default branch instead — the right choice when developing Pipecat itself or building against unreleased code:

```bash
pipecat context-hub refresh --framework-version v1.7.0
pipecat context-hub refresh --framework-version head
```

### Without the Pipecat CLI

The hub runs standalone too. [`uvx`](https://docs.astral.sh/uv/), uv's one-shot runner, fetches and runs it on demand with nothing installed:

```bash
uvx pipecat-ai-context-hub refresh   # build local index
```

Every command on this page works either way — `pipecat context-hub refresh` and `uvx pipecat-ai-context-hub refresh` are the same command.

<Tip>
  To install it once instead of fetching on demand, run `uv tool install
  pipecat-ai-context-hub`. This puts the command on your `PATH` under the
  shorter `pipecat-context-hub` name, so you drop the `uvx` prefix. The index
  lives in one place per machine, so a standalone install and the CLI's bundled
  copy share it rather than each building their own.
</Tip>

## Custom sources

Point the hub at your own repositories with `PIPECAT_HUB_EXTRA_REPOS`, a comma-separated list of GitHub `org/repo` slugs. These are indexed alongside the default Pipecat repos, so your private code is searchable next to the framework. Set the variable, then run `refresh`:

```bash
PIPECAT_HUB_EXTRA_REPOS="your-org/your-repo,your-org/another-repo" \
  uvx pipecat-ai-context-hub refresh
```

The hub also reads a `.env` file from the directory you run the command in, so you can keep the list there instead of exporting it each time:

```bash
# .env
PIPECAT_HUB_EXTRA_REPOS="your-org/your-repo,your-org/another-repo"
```

Slugs that duplicate a default repo are deduped automatically, so it's harmless to leave them in. Your custom repos then surface through the same `search_*` and `get_*` tools as the framework.

<Note>
  Only Python (`.py`/`.pyi`), TypeScript (`.ts`/`.tsx`), and RST (`docs/**.rst`)
  files are parsed into the searchable index. Other languages (for example
  Swift, Kotlin, or C++ SDKs) are cloned but won't surface in `search_api` or
  `get_code_snippet`.
</Note>

<Tip>
  The hub clones with standard git, so private repos index fine as long as your
  local git is already authenticated to GitHub — via an SSH key or a git
  credential helper. The hub itself adds no token configuration. See the repo's
  [`.env.example`](https://github.com/pipecat-ai/pipecat-context-hub/blob/main/.env.example)
  for ready-made repo bundles.
</Tip>

## Tools

| Tool                | Use it to                                                                                            |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `search_docs`       | Find guides and conceptual docs ("how do I ...?")                                                    |
| `search_examples`   | Find working example code by task or component                                                       |
| `search_api`        | Find class definitions, method signatures, frame types, and inheritance                              |
| `get_doc`           | Fetch a full doc page by ID or path                                                                  |
| `get_example`       | Fetch the full source files for an example                                                           |
| `get_code_snippet`  | Fetch targeted code by symbol, intent, or file and line range                                        |
| `check_deprecation` | Check whether an import path is deprecated or removed (can evaluate lifecycle at a specific version) |
| `get_hub_status`    | Report index health, freshness, and the indexed Pipecat version                                      |

The three `search_*` tools return a ranked list of hits, each with a relevance
`score`. Each response also carries an evidence report with an overall
`confidence`, a `low_confidence` flag, and suggested follow-up queries. The
agent triages that list, picks the best fit, then calls `get_doc`, `get_example`,
or `get_code_snippet` to pull detailed content. The coding agent can pass its
`pipecat_version` to score and filter results for compatibility with the version
it targets. `check_deprecation` and `get_hub_status` can be called directly to
inspect symbol lifecycle and index health.

To make your coding agent reach for these tools automatically, add the [recommended CLAUDE.md / AGENTS.md instructions](https://github.com/pipecat-ai/pipecat-context-hub/blob/main/docs/README.md#add-claudemd-instructions-recommended) to your project.

## CLI lookups

Every tool is also a one-shot CLI command, so you can query the index from a shell with no MCP setup. Reach for this when you need a single answer fast, like a deprecation check, an API signature, or an index health check. Each command prints the tool's JSON to stdout:

```bash
pipecat context-hub check-deprecation PipelineTask      # is this symbol deprecated?
pipecat context-hub search-api "WebsocketServerParams"  # find an API signature
pipecat context-hub status                              # index health / freshness
```

Or, without the Pipecat CLI, the same commands under `uvx pipecat-ai-context-hub`. The [`pipecat context-hub` reference](/api-reference/cli/context-hub) documents every command and flag.

## MCP server

For a longer build or debugging session where the model probes the index repeatedly, add the hub as an MCP server instead of shelling out per query. It keeps the index warm for the whole session and exposes the same tools to your coding tool directly.

`pipecat context-hub install` does this for you wherever the client ships its own CLI, and prints the config to paste where it doesn't:

```bash
pipecat context-hub install                     # every detected client, then build the index
pipecat context-hub install --client cursor     # print the config for one client
pipecat context-hub install --print-config      # show what would be registered, change nothing
```

To register by hand instead:

## Keeping the index current

A stale index is invisible: your agent answers just as confidently from month-old APIs, and you find out when the generated code doesn't match the version you're running. So the Pipecat CLI checks on the way past and prints a one-line notice on stderr when something needs attention. For example, it might print:

```
⚠ Pipecat Context Hub index is 42 days old — run `pipecat context-hub refresh` so coding agents don't cite stale APIs.
⚠ Pipecat Context Hub index was built for pipecat-ai 1.2.0, but this project uses 1.6.0 — run `pipecat context-hub refresh` so coding agents match your version.
```

The version comparison is deliberately quiet. It compares only major and minor, so a patch or dev release never triggers it, and it stays silent when your project has an editable Pipecat checkout or when the index is _ahead_ of your project — an index built from `main` legitimately runs ahead of a released version.

The notice is silent when no index exists, so it never appears for people who don't use the hub. Two environment variables tune it:

- `PIPECAT_HUB_STALE_AFTER_DAYS` — index age in days before it's called stale. Defaults to `7`; `0` disables the age check.
- `PIPECAT_HUB_CHECK=0` — turn the notice off entirely.
