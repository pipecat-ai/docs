## Overview

`BotWorkingIdleProcessor` tells your app when the bot has gone quiet at work.
An agentic pipeline leaves silences the user can't tell from a hang: the wait
for the LLM's first token, and the wait for each tool call. The processor
watches the reply and function-call frames, and fires
`on_bot_working_idle(kind, function_name)` when a wait runs long. What to say
about it — a phrase, a clip, nothing — is the app's decision.

The split is the same as `UserIdleController` on the user side: the signal
knows *that* the bot is quietly working; the handler decides *what* happens.

The processor also watches the transport's `BotStarted/StoppedSpeakingFrame`
upstream, so nothing fires while the bot is actually speaking. A wait that
expires mid-speech is held and fires the moment the silence opens.

The default action (`speak_filler`) speaks through your real TTS with
`append_to_context=False`, so fillers behave like any other utterance for turn
tracking, RTVI events and interruptions, and never reach the LLM context.

## Installation

This is a community-maintained package distributed separately from `pipecat-ai`:

```bash
uv add pipecat-thinking-backchannel
```

## Prerequisites

No account or API key of its own.

- **Pipecat 1.6.0 or later**: `pipecat-ai>=1.6.0,<2`
- **A pipeline agent** (STT, LLM, TTS): the signal watches reply and
  function-call frames; speech-to-speech models don't emit them
- **A TTS service**, if you use the default `speak_filler` action

## Configuration

Constructor arguments for `BotWorkingIdleProcessor`. Every default works
unconfigured.

<ParamField path="params" type="BotWorkingIdleParams" default="None">
  The dials for the wait timings and how chatty the signal is. See
  [Params](#params) below.
</ParamField>

### Params

Runtime tuning passed via the `params` constructor argument using
`BotWorkingIdleParams(...)`.

| Parameter          | Type    | Default | Description                                                                                     |
| ------------------ | ------- | ------- | ----------------------------------------------------------------------------------------------- |
| `llm_delay_s`      | `float` | `1.0`   | How long the bot must be quiet waiting for its first token before the event fires.               |
| `tool_delay_s`     | `float` | `0.8`   | How long the bot must be quiet waiting on a tool. Parallel calls re-arm the timer, never stack.   |
| `cooldown_s`       | `float` | `4.0`   | Minimum time between two events.                                                                 |
| `fire_probability` | `float` | `0.9`   | Chance of firing at an otherwise eligible moment. Below 1.0, or it sounds mechanical.             |
| `max_per_episode`  | `int`   | `2`     | Most events within one reply, from the first arm until the reply ends or an interruption lands.   |

<Note>
  The processor adds no inference: it is a frame state machine with one
  timer — no VAD, no turn model, no ONNX. See the [source
  repository](https://github.com/iamdgarcia/pipecat-thinking-backchannel) for
  the authoritative, up-to-date list of parameters and defaults.
</Note>

## Usage

Place the processor between the LLM and the TTS, and wire the event. The
default action speaks a filler through your real TTS, out of the LLM context:

```python
from pipecat_thinking_backchannel import (
    BotWorkingIdleProcessor,
    speak_filler,
)

idle = BotWorkingIdleProcessor()
idle.add_event_handler("on_bot_working_idle", speak_filler(tts))

pipeline = Pipeline([
    transport.input(),
    stt,
    context_aggregator.user(),
    llm,
    idle,  # between the LLM and the TTS
    tts,
    transport.output(),
    context_aggregator.assistant(),
])
```

Bring your own words, keyed by signal kind:

```python
idle.add_event_handler(
    "on_bot_working_idle",
    speak_filler(tts, {
        "llm": ("Let me think.", "Good question."),
        "tool": ("Let me check on that.", "One moment."),
    }),
)
```

Or handle the event yourself — the event carries `function_name`, so per-tool
phrases and learned tool durations are a small handler away:

```python
@idle.event_handler("on_bot_working_idle")
async def on_bot_working_idle(processor, kind, function_name=None):
    phrase = PHRASES.get(function_name) or PHRASES[kind]
    await tts.queue_frame(TTSSpeakFrame(phrase, append_to_context=False))
```
