The `project` command manages everything you deploy and run. A project is an agent with environments, and each environment is an agent of its own, so one group covers both: a command names the project, and `--env` reaches one of its environments.

```shell
pipecat cloud project status my-bot
pipecat cloud project status my-bot --env staging
pipecat cloud project logs my-bot --env pr-7
```

An agent's own name works anywhere a project name does, so `project status my-bot-pr-7` addresses the same preview as `--env pr-7`. The project is its own `production` environment, so `--env production` means the project itself, exactly as naming it with no `--env` does.

For the concepts behind the environment commands, see [Projects and environments](/pipecat-cloud/fundamentals/projects-and-environments).

<Warning>
  `pipecat cloud agent` is deprecated. Every command below still works under
  that name and prints a notice on stderr. Use `project`, with `--env` to
  address an environment.
</Warning>

## start

Start a deployed agent instance, creating an active session.

**Usage:**

```shell
pipecat cloud project start [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="agent-name" type="string">
  Unique string identifier for the agent deployment. Must not contain spaces.
  Defaults to `agent_name` in `pcc-deploy.toml`.
</ParamField>

**Options:**

<ParamField path="--env" type="string">
  Act on this environment of the project rather than on the project itself.
  Addressing an agent by its own name works just as well.
</ParamField>

<ParamField path="--config-file" type="string">
  Path to an alternate deploy config file. Defaults to `pcc-deploy.toml`.
</ParamField>

<ParamField path="--api-key / -k" type="string">
  Public API key to authenticate the agent deployment. Will default to any key
  set in your config.

For more information, see [API keys](/pipecat-cloud/fundamentals/accounts-and-organizations#api-keys).

</ParamField>

<ParamField path="--data / -d" type="string">
  Stringified JSON object to pass to the agent deployment. This data will be 
  available to the agent as a `data` parameter in your `bot()` method.

More information [here](/pipecat-cloud/fundamentals/active-sessions#running-an-agent).

</ParamField>

<ParamField path="--force / -f" type="boolean" default="false">
  Skip summary confirmation before issuing start request.
</ParamField>

<ParamField path="--use-daily / -D" type="boolean" default="false">
  Create a Daily WebRTC session for the agent.
</ParamField>

<ParamField path="--daily-properties / -p" type="string">
Stringified JSON object with Daily room properties to customize the WebRTC
session. Only used when `--use-daily` is set to true.

See [Daily API
documentation](https://docs.daily.co/reference/rest-api/rooms/config) for
available properties.

</ParamField>

<ParamField path="--organization / -o" type="str">
  Organization to start the agent for. If not provided, uses the current
  organization from your configuration.
</ParamField>

## status

Shows the current status of an agent deployment, including health and conditions, the deployment's CPU architecture, and its resolved resources (CPU and memory). For agents deployed with explicit resources rather than a profile, this is where the sizing is shown.

**Usage:**

```shell
pipecat cloud project status [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="agent-name" type="string" required>
  Unique string identifier for the agent deployment. Must not contain spaces.
</ParamField>

**Options:**

<ParamField path="--env" type="string">
  Act on this environment of the project rather than on the project itself.
  Addressing an agent by its own name works just as well.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the agent belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

For a [GitHub-linked agent](#link), the output also carries the linked
repository and branch, the Dockerfile path and build subdirectory, whether
pushes auto-deploy, the commit actually running, and the latest deploy attempt
with its failure reason if it has one.

The running commit and the linked branch can legitimately differ — right after
you link a repository, after you re-point an agent, or when auto-deploy is off
and there are unshipped commits. When the running commit didn't come from the
current link, `status` says so and names the repository and branch it did come
from.

<Tip>
  Nothing live from the current link shows as `— (nothing from this link is live
  yet)`, which is what you'll see between `project link` and the first [`project
  deploy --github`](#deploy).
</Tip>

For a project with a repository connected, the output also carries its [watch
paths](/pipecat-cloud/guides/deploy-from-github#watch-paths), whether [PR
previews](/pipecat-cloud/guides/pr-previews) are on and which secret set they
mount, and whether pull requests opened by bots get previews.

For an environment it carries the project it belongs to and its environment
name instead, and for a PR preview the pull request it deploys.

Its environments are a listing of their own: see [`env list`](#env-list).

## link

Link an agent to a GitHub repository and branch, or re-point an existing link. Requires the organization to be [connected to GitHub](/api-reference/cli/cloud/github#connect).

**Usage:**

```shell
pipecat cloud project link [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="agent-name" type="string" required>
  Name of the agent to link.
</ParamField>

**Options:**

<ParamField path="--env" type="string">
  Act on this environment of the project rather than on the project itself.
  Addressing an agent by its own name works just as well.
</ParamField>

<ParamField path="--repo" type="string" required>
  Repository as `owner/repo`.
</ParamField>

<ParamField path="--branch" type="string" required>
  Branch to build and deploy from.
</ParamField>

<ParamField path="--dockerfile-path" type="string" default="Dockerfile">
  Path to the Dockerfile within the repository.
</ParamField>

<ParamField path="--subdirectory" type="string">
  Build context subdirectory within the repository.
</ParamField>

<ParamField
  path="--auto-deploy / --no-auto-deploy"
  type="boolean"
  default="--auto-deploy"
>
  Whether a push to the branch deploys the agent.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the agent belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

```shell
pipecat cloud project link my-agent --repo my-org/my-bot --branch main
```

<Note>
  Linking never changes what is running. It sets where the *next* deploy comes
  from — use [`project deploy --github`](#deploy) to ship the branch now.
</Note>

Re-running `link` on an already-linked agent re-points it. Options you leave out keep their stored values, so changing only the branch won't reset a Dockerfile path you set earlier.

The repository and branch are validated locally against the same rules the API applies, so a typo fails immediately rather than after a round trip.

## deploy

Build and deploy a GitHub-linked agent from its branch's current HEAD, without waiting for a push.

**Usage:**

```shell
pipecat cloud project deploy [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="agent-name" type="string" required>
  Name of the agent to deploy.
</ParamField>

**Options:**

<ParamField path="--env" type="string">
  Act on this environment of the project rather than on the project itself.
  Addressing an agent by its own name works just as well.
</ParamField>

<ParamField path="--github" type="boolean" default="false">
  Deploy the agent's linked GitHub branch. Currently the only mode this command
  supports, so it has to be passed — without it the command exits 1 and points
  you at `pipecat cloud deploy`.
</ParamField>

<ParamField path="--wait" type="boolean" default="false">
  Follow the deploy rather than returning as soon as it is queued.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the agent belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

```shell
pipecat cloud project deploy my-agent --github --wait
```

<Note>
  `--github` is explicit rather than implied so that adding image-based deploys
  to this command later can't change what an existing script does. To deploy an
  image or a cloud build, use [`pipecat cloud
  deploy`](/api-reference/cli/cloud/deploy).
</Note>

### What `--wait` reports

Without `--wait`, the command returns once the deploy is queued, printing the branch and commit it will build.

With `--wait`, it follows the deploy and reports one of these:

| Outcome        | Meaning                                                                          | Exit                       |
| -------------- | -------------------------------------------------------------------------------- | -------------------------- |
| Succeeded      | The deploy reached a terminal state and succeeded.                               | 0                          |
| Failed         | The deploy reached a terminal state and failed. The reason is printed.           | 1 (0 with `--output json`) |
| Superseded     | A newer push took over as the latest attempt, so this one is no longer reported. | 0                          |
| Still building | Observed and still moving when the wait ran out. It continues server-side.       | 0                          |
| Never observed | The wait never saw the attempt at all.                                           | 1                          |

<Warning>
  A zero exit from `--wait` means the deploy was observed and did not fail, not
  that it finished. A deploy still building, or superseded by a newer push, also
  exits 0. With `--output json`, a failed deploy exits 0 as well: `waitOutcome`
  is `terminal` for both a success and a failure, so gate on
  `latestDeploy.status` being `succeeded`.
</Warning>

"Never observed" exits non-zero on purpose: a wait that saw nothing can't tell a healthy build from an API that was down the whole time, and calling that success is what would make `--wait` unsafe as a deploy gate.

## sessions

Lists active sessions for a specified agent. When there are no active sessions, it suggests how to start a new session.

The Status column distinguishes how each session ended: sessions that ended before reaching an agent ("Ended before agent start"), activation timeouts ("Timeout"), and agent errors are shown separately from completed sessions.

When used with the `--id` option, displays detailed information about a specific session including CPU and memory usage with sparkline visualizations and percentile summaries, plus lifecycle events showing when the request arrived, when the agent started serving it, and when the session ended.

**Usage:**

```shell
pipecat cloud project sessions [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="agent-name" type="string">
  Name of the agent to list active sessions for. Defaults to `agent_name` in
  `pcc-deploy.toml`.
</ParamField>

**Options:**

<ParamField path="--env" type="string">
  Act on this environment of the project rather than on the project itself.
  Addressing an agent by its own name works just as well.
</ParamField>

<ParamField path="--config-file" type="string">
  Path to an alternate deploy config file. Defaults to `pcc-deploy.toml`.
</ParamField>

<ParamField path="--id / -i" type="string">
  Session ID to view detailed metrics for. When provided, displays CPU and
  memory usage statistics including sparkline visualizations and percentile
  summaries (p50, p90, p99).
</ParamField>

<ParamField path="--end-state" type="string">
  Filter sessions by how they ended. Known values: `active`, `completed`,
  `ended_before_agent_start`, `agent_start_timeout`, `terminated`,
  `agent_error`, `unknown`. Other values are passed to the API, so states added
  after this CLI release still filter.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization to list sessions for. If not provided, uses the current
  organization from your configuration.
</ParamField>

### env add

Link an existing agent as an environment of a project.

**Usage:**

```shell
pipecat cloud project env add [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="project" type="string" required>
  Name of the project the environment belongs to.
</ParamField>

<ParamField path="name" type="string" required>
  What to call it among the project's environments. Two to 50 lowercase letters,
  digits and dashes, starting and ending with a letter or digit. `production` is
  the project itself, and names starting with `pr-` are reserved for PR
  previews.
</ParamField>

**Options:**

<ParamField path="--agent" type="string" required>
  Name of the existing agent to link as this environment.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the project belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

```shell
pipecat cloud project env add my-bot staging --agent my-bot-staging
```

The agent has to exist already. Create it with [`pipecat cloud
deploy`](/api-reference/cli/cloud/deploy), then link it.

Linking changes nothing about what the agent runs: it keeps its own repository
link, secret sets and scaling, and follows the project's watch paths from here.
Re-running `env add` with a different name renames the environment, and with a
different project moves it.

The name is checked locally against the same rules the API applies, so a typo
fails immediately rather than after a round trip. The API refuses the link when
the agent is in another region than the project, when either side already has
environments, when the project has PR previews on, when the name is taken by
another environment, or when the agent is a PR preview.

### env promote

Deploy an environment's running code onto the project.

**Usage:**

```shell
pipecat cloud project env promote [ARGS] [OPTIONS]
```

**Arguments:**

<ParamField path="project" type="string" required>
  Name of the project to deploy onto.
</ParamField>

<ParamField path="name" type="string" required>
  Environment to promote, by its environment name.
</ParamField>

**Options:**

<ParamField path="--force / -f" type="boolean" default="false">
  Skip the confirmation prompt.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the project belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

```shell
pipecat cloud project env promote my-bot staging
```

It deploys the build behind the environment's active deployment, or the image it
was deployed from. Nothing is rebuilt.

Promotion moves code only: the project keeps its own secrets, scaling and agent
profile. An environment with nothing deployed has nothing to promote, and the
command says so and exits 1.

The command returns once the API has accepted the deploy; the rollout follows.
Watch it with `pipecat cloud project status my-bot`.

## profiles

<SelfHostedCliNote />

The `profiles` sub-commands manage organization-defined agent profiles for [self-hosted regions](/pipecat-cloud/enterprise/sizing#organization-agent-profiles). A profile is a named CPU and memory shape selected with `--profile` on deploy. Profile edits apply to future deploys only: running agents keep the resources their deployment captured.

Lists the platform's agent profiles plus any your organization has defined, with CPU, memory, source, and whether each is enabled.

**Usage:**


**Options:**

<ParamField path="--organization / -o" type="string">
  Organization to list profiles for. If not provided, uses the current
  organization from your configuration.
</ParamField>

### profiles create

Create an organization-defined profile.

**Usage:**

```shell
pipecat cloud project profiles create [NAME] --cpu [CPU] --memory [MEMORY] [OPTIONS]
```

  The profile's name, used with `--profile` on deploy. Lowercase letters,

</ParamField>

### profiles update

Change a profile's sizing or display name. CPU and memory are updated together.

**Usage:**

```shell
pipecat cloud project profiles update [NAME] [OPTIONS]
```

**Options:**

<ParamField path="--cpu" type="string">
  New CPU quantity. Requires `--memory`.
</ParamField>

<ParamField path="--memory" type="string">
  New memory quantity. Requires `--cpu`.
</ParamField>

<ParamField path="--display-name" type="string">
  New human-readable name.
</ParamField>

<ParamField path="--organization / -o" type="string">
  Organization the profile belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

### profiles disable

Retire a profile from new deploys. Existing deployments are unaffected. Disabling is reversible with `enable`.

**Usage:**

```shell
pipecat cloud project profiles disable [NAME] [OPTIONS]
```

**Options:**

<ParamField path="--organization / -o" type="string">
  Organization the profile belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>

### profiles enable

Re-enable a disabled profile for new deploys.

**Usage:**

```shell
pipecat cloud project profiles enable [NAME] [OPTIONS]
```

**Options:**

<ParamField path="--organization / -o" type="string">
  Organization the profile belongs to. If not provided, uses the current
  organization from your configuration.
</ParamField>
